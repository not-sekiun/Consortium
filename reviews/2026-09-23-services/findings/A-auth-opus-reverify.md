PEP 758 (Python 3.14, `requires-python >=3.14`) permits an unparenthesized exception tuple in `except` when there is no `as`, so the line compiles and means "catch JSONDecodeError or KeyError", matching the comment at :384-388. The original "SyntaxError, server won't boot" claim was a false positive; AGENTS.md is correct.

- **[CONFIRMED] Passwords stored, compared and persisted in plaintext with a non-constant-time compare** — user_accounts_service.py:331 — `user_account.password != password` compares two `str`; `UserAccountModel.password: str` (user_account_models.py:9) is never hashed anywhere, is echoed verbatim to disk at :547-548, and `str.__ne__` short-circuits at the first differing byte. - **[REFINED] Plaintext passwords written to logs** — user_accounts_service.py:264-269 (explicit) plus the `{!r}` sites — The explicit INFO leak at :264-269 (logs `old_password` and `password`) is CONFIRMED, as is the root cause that `UserAccountModel` overrides only `__str__` (user_account_models.py:12) and not `__repr__`, so `{!r}` renders `password`. But the enumerated `{!r}` line list is wrong. Verified by grep: the true `{!r}` (leaking) sites are :93, :112, :303, :334, :675. Lines :507 (`"Read user account: {}"`) and :544 (`"Writing user account: {}"`) use `{}` -> `__str__` and do NOT leak, yet the prior finding listed both as leaks; and it MISSED :303 (`self._logger.debug("- {!r}", deleted_user_account)`), which does leak the deleted account's password. Severity high stands; the citations need the above correction.

- **[REFINED] Username-existence timing oracle in `authenticate_user_account_credentials`** — user_accounts_service.py:324-332 — A timing signal plausibly exists and the enumeration risk is real, so the finding is kept, but the stated mechanism is imprecise. It is not true that "for an unknown username the method raises immediately": BOTH paths first run the full O(n) scan at :324-326 to build `existing_usernames`. Unknown then does a second full scan in `get_user_account_by_username` (:110-114) and raises; known does a partial scan plus one plaintext compare. The dominant cost on both paths is the linear scan(s), so the presence/absence delta is small and can even run opposite to the naive expectation; the sharper side channel here is actually the prefix-length leak of the plaintext `!=` compare on the known path. Med is defensible; treat as "weak timing + compare-prefix oracle", not "immediate-raise oracle".

- **[CONFIRMED] Any operator can subscribe to every event type — no per-event authorization** — events_websocket_service.py:257-308; websockets_api.py:120-123 — Verified end to end: the only gate is one `USE_EVENTS_WEBSOCKET` check in `authenticate_websocket_connection` at the handshake (websockets_api.py:122). `_handle_subscribe_action` registers the sender for any `EventType` value with no role/ownership filter, and `user` is never passed into the handler at all (`handle_connection` at :457-483 only logs it). ## New findings (missed by the prior pass)

### [SEV: med] A live events websocket is authorized once at handshake and never re-checked, so revocation does not take effect until disconnect
- **File:** consortium/server/services/events_websocket_service.py:379-440 (`run`), 457-483 (`handle_connection`)
- **Category:** security
- **What:** `handle_connection` resolves `user` and its permission only at the handshake, then `run` loops for the entire connection lifetime with no re-validation of the account, its role, or the `USE_EVENTS_WEBSOCKET` permission. Nothing in these files (or an external revocation path) can terminate an established connection or drop its registered sender.
- **Failure scenario:** Operator A opens the events socket and subscribes. An admin then deletes A's account, downgrades A's role, or strips `USE_EVENTS_WEBSOCKET` (via `update_user_account_by_user_account_id` / role edits). A's socket stays registered with the events service and keeps receiving every subscribed event indefinitely. Combined with the confirmed all-events subscription gap, a de-authorized operator retains a full live feed of server activity until they choose to disconnect.
- **Fix:** Periodically (or on each received frame) re-resolve the user via the users service and re-check the permission inside `run`, closing the socket and calling `_deregister_all_subscriptions` when the account is gone or no longer authorized; or provide a server-side revocation hook that closes affected connections. At minimum document that events-socket authorization is handshake-time-only and survives revocation.

### [SEV: low] Unbounded per-connection event-subscription work on an authenticated-but-hostile socket
- **File:** consortium/server/services/events_websocket_service.py:257-308, 383
- **Category:** dos
- **What:** `run` calls `receive_json` with no frame-size bound, and `_handle_subscribe_action` accepts an arbitrarily large `events` list, doing O(n*m) membership checks against `list(EventType)` per message. The handshake rate limit (20/min) governs ticket issuance, not the number or size of action frames on an already-open socket.
- **Failure scenario:** A hostile authenticated operator streams very large action messages on a single open socket, consuming CPU/memory server-side without tripping the ticket rate limiter.
- **Fix:** Consistent with the repo's "policy at the boundary" stance, cap the accepted frame size and/or the `events` list length at this service boundary (or document that the socket trusts an authenticated operator not to abuse frame size). Low priority; authenticated-only.
