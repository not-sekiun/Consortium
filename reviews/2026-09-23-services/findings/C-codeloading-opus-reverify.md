## Verdicts on prior findings

**[REFINED] `entry_point` module used to build path/import with no confinement** — component_loader_service.py:278-297. The missing `.resolve()`/`is_relative_to` confinement is genuinely absent (accurate). But the stated exploit — reload/import of an arbitrary *framework* module under `consortium_root` via `..`/absolute segments — is **not reachable**: `component_module.split(".")` (line 280) can never emit a `..` parent segment (any all-dot string splits to empty parts, which pathlib drops), and an absolute/drive-rooted segment resets the path *outside* `consortium_root` so `relative_to` (295) raises `ValueError` (that is finding 2) instead of importing anything. Every *successful* import is therefore forced to descend within the plugin's own directory, and the derived dotted name is always `consortium.components.plugins.<plugin>...`, which cannot match a live framework module already in `sys.modules` (303) — so no framework-module reload/import occurs. Residual real risks are plugin-controlled only (nested-plugin reload collision; an in-plugin `.py` that is a symlink to arbitrary code), which the "`.py` bodies execute by design" trust model already permits. Net: hardening (reject separators/`..`/leading dots, resolve + `is_relative_to(component_directory)`) is still worth doing, but this is low, not high.

**[CONFIRMED w/ REFINED reachability] Malformed `entry_point` -> uncaught `ValueError` from `relative_to` = startup DoS** — component_loader_service.py:295-297 (outside the try at 300), catch set 478-489, wrap_filesystem_errors is `OSError`-only (utils.py:100/118). `ValueError` is not caught anywhere on the path up through `load_framework_plugins` (plugins_service.py:496, untried), so one bad manifest aborts the whole scan and startup. The defect stands. Correction: the prior example `entry_point: "C:/Users/x/evil:Sym"` does **not** work — `entry_point.split(":", 1)` (line 191) consumes the drive colon, yielding module `"C"`, so it becomes a harmless not-found. A real trigger is an absolute/drive-relative path with dot-free directory components pointing at an existing `.py`, e.g. on Linux `entry_point: "/usr/lib/python3/dist-packages/six:Anything"` (module has no dots, resolves absolute outside the tree, `six.py` exists -> `relative_to` raises). Practical severity med (needs an existing out-of-tree `.py`), defect real.

**[CONFIRMED, strengthened] Async load path skips duplicate-label and component-dependency validation** — component_registry_service.py:120-137 (`load_component`: id check only) vs 81-101 (`register_component`: id + label + `validate_component_component_dependencies`). Reached via plugins_service.py:332-336. Additionally: because `plugin_id` is a fresh `uuid.uuid4()` per instantiation (base_plugin.py:100), the id check on this path is almost always a no-op, so *label* is the only effective duplicate guard — and it is exactly what `load_component` omits. This makes the gap more serious than "silently accepted": individual load/reload has essentially no duplicate protection.

**[REFINED — mechanism largely refuted] TOCTOU in `load_component` (id check / insert straddle `await`)** — component_registry_service.py:127/132/136, no lock on `self._components` (32). The absent lock is real, but the described outcome ("both pass the id check, double-start, one overwritten in the registry") cannot occur for any component here: `_get_component_id` returns a fresh `uuid4` per instantiation (base_plugin.py:100; other domains likewise use per-instance ids), so two concurrent loads of the same directory produce two *different* ids — neither overwrites the other and the id check never trips. The genuine defect is the absence of directory/label-level dedup + locking, which lets the same directory become two coexisting, both-started instances (see new reload-dedup finding). The only true id race (same instance object passed twice) is not exercised by any flow.

**[CONFIRMED] `reload_component_by_component_id` unloads before loading with no rollback** — component_registry_service.py:177-187. ## New findings (missed by the prior pass)

### [SEV: med] `reload_framework_plugins` "already-loaded" dedup compares the wrong path level, re-loading a failed-to-unload plugin as a duplicate
- **File:** plugins_service.py:689 (`if plugin.root_directory.parent == path.parent:`)
- **Category:** error-handling / design
- **What:** After unloading all plugins, reload rescans and skips any manifest whose plugin is still loaded (i.e. failed to unload). The skip test compares `plugin.root_directory.parent` against `path.parent` (the manifest's directory). For the normal layout, `root_directory` is the plugin directory itself (base_plugin.py:113-115 sets it to `parents[0]` of the entry-point `.py`, and the entry-point `.py` sits directly in the plugin dir — e.g. persistent_listeners/plugin.py), so `root_directory.parent` is the *plugins* directory while `path.parent` is the *plugin* directory. They never match, so `plugin_loaded` stays `False`.
- **Failure scenario:** A plugin fails to unload (still registered) during `reload_framework_plugins` with `force_reload=False`. The dedup fails to recognise it, a second instance is instantiated (fresh `uuid4`) and started from the same directory, leaving two coexisting registered+running instances of the same plugin (id-based `already_registered` cannot catch it because the ids differ). Conversely, for a plugin whose entry point lives one level deep in a subpackage the comparison spuriously *matches*, so a legitimately-needed reload can be skipped.
- **Fix:** Store and compare the load directory (the manifest's directory) directly, e.g. skip when an already-loaded plugin's manifest directory equals `path.parent`; do not derive it from `root_directory`, which can be nested. Combine with a load lock so the rescan/load is serialised.

### [SEV: med] Non-domain exceptions from `_post_validate_component_object` escape the per-component catch set -> discovery/startup DoS
- **File:** component_loader_service.py:445 (unguarded `_post_validate_component_object` call) and 478-488 (batch catch set); agent_profile_loader_service.py:95-97; listener_profile_loader_service.py:85
- **Category:** dos / error-handling
- **What:** `get_component_from_directory` calls `_post_validate_component_object` outside any try/except. For agent and listener profiles this hook executes component-author code — `component_object.agent_type()` / `component_object.listener_type()` and attribute wiring. Any exception that is not a `Component*Error` / `ComponentConfigurationError` / `ComponentDependencyError` / domain framework error (e.g. a plain `TypeError`, `AttributeError`, `KeyError` from a buggy `agent_type.__init__`, or `agent_generator` being `None`) is not in the batch loop's catch set (478-488) and propagates out of `get_all_components_from_directory`.
- **Failure scenario:** One broken agent/listener profile on disk whose `agent_type()`/`listener_type()` raises an ordinary exception aborts the entire discovery scan at startup, so every other profile in the directory also fails to load — the exact "one bad component becomes a global DoS" pattern the batch loop is meant to prevent. (Same structural gap that produces the `ValueError` in finding 2, but reachable without any absolute-path trickery.)
- **Fix:** Guard `_post_validate_component_object` (and ideally wrap the whole per-directory body) so unexpected exceptions become an `internal_error`/`interface_error` for that one component, and add a catch-all in the batch loop that records `(directory, exc)` instead of propagating.

### [SEV: low] `importlib.reload` on a genuine plugin reload re-runs module top-level and `__init_subclass__`, duplicating class objects
- **File:** component_loader_service.py:303-306
- **Category:** design / error-handling
- **What:** When a plugin's computed module is already in `sys.modules` (the normal reload case), the loader calls `importlib.reload`, which re-executes the module body and re-fires `__init_subclass__` (base_plugin.py:112-120 registers `root_directory`/`services` and validates metadata there; the loader's own comment at 309-311 notes framework registration happens via `__init_subclass__` at import time). Reload produces a *new* class object while any references held elsewhere (subclass registries populated via `__init_subclass__`, `isinstance` checks, cached types) still point at the old one.
- **Failure scenario:** Operator reloads a running plugin; a framework registry keyed by class identity now holds both the stale and the fresh class, and `isinstance`/identity checks against the old class silently fail for the new instance. Import side effects in the module run a second time.
- **Fix:** Prefer discarding the stale module (`sys.modules.pop` + fresh `import_module`) over `reload`, or document reload as identity-breaking and ensure registries are keyed by a stable id rather than the class object.

## Notes
- Windows drive-letter paths in `entry_point` are neutralised by `entry_point.split(":", 1)` (component_loader_service.py:191) consuming the drive colon; this both limits the finding-1 traversal surface and invalidates the finding-2 example. Worth a human confirming the intended deploy OS; the `relative_to` fix should be applied regardless.
- `_attach_third_party_dependencies_to_component_class` (component_loader_service.py:262-268) sets `component_class.third_party_dependencies` on the *class* object. If the same class object is ever reused across two loads (nested-plugin reload collision, or an in-plugin symlink resolving two manifests to one file), the second load's dependency set overwrites the first's on the shared class. Low, plugin-controlled, but a latent shared-mutable-state hazard.
- The manifest JSON schema (`entry_point`/`enabled`, `additionalProperties: False`) is still duplicated verbatim across the four domain loaders; hoisting it (design note from the prior pass) remains the right home for any `entry_point` hardening so it is enforced once.
- Confirmed no `eval`/`exec`/`pickle`/`yaml.unsafe_load`/archive extraction in scope; `pyproject.toml` via `tomllib` and dependencies only version-checked via `importlib.metadata.version` (never imported). The only dynamic-execution surface remains the `importlib` entry-point path. `normalize_uuid` is `str(value)` (utils.py:169-170), so a malformed id cleanly becomes not-found. The `event_hook_registry_service` register-then-rollback pattern (40-125) remains the model the plugin reload path (finding 5) should follow.
